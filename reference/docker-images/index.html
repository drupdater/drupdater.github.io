    Docker images¶

    Drupdater ships as a Docker image containing the Go binary plus the PHP runtime, Composer, Drush's dependencies and the helper scripts it needs. There is no other supported distribution.

    Published images¶

    ghcr.io/drupdater/drupdater-php8.3
ghcr.io/drupdater/drupdater-php8.4
ghcr.io/drupdater/drupdater-php8.5

    Pick the variant matching your project's PHP version. A mismatch is caught by the PHP platform requirements satisfied preflight check rather than failing obscurely later.

    Images are built for linux/amd64 and linux/arm64, with build provenance attestation pushed to the registry.

    Tags¶

    Each variant is tagged on release:

    Tag form Example Moves?
    <major>.<minor>.<patch> 0.3.6 No
    v<major>.<minor>.<patch> v0.3.6 No
    <major>.<minor> 0.3 Yes, within the minor
    <major> 0 Yes, within the major
    latest Yes, always

    Pin in production

    Drupdater is pre-1.0. The CLI surface and config format may change between minor versions, so latest and the floating 0 tag can change behaviour under you.

    The examples throughout this documentation use latest for brevity. In a scheduled pipeline, replace it with the full version from the latest release and bump it deliberately.

    Entrypoint¶

    The binary lives at /opt/drupdater/bin and is the image's ENTRYPOINT.

    This matters in GitLab CI, where the image is used as a job container and its entrypoint must be cleared before script: can run:

    image:
  name: ghcr.io/drupdater/drupdater-php8.3:latest
  entrypoint: [""]
script:
  - /opt/drupdater/bin "$DRUPDATER_TOKEN"

    In GitHub Actions the container is used the same way, so the full path is needed there too:

    container:
  image: ghcr.io/drupdater/drupdater-php8.3:latest
steps:
  - run: /opt/drupdater/bin "${{ secrets.DRUPDATER_TOKEN }}"

    Run directly with docker run, the entrypoint applies and you pass only arguments:

    docker run ghcr.io/drupdater/drupdater-php8.3:latest <token> --dry-run

    What is in the image¶

    Built on php:<version>-cli-trixie, with:

    • PHP extensions — pdo_mysql, gd, zip, imagick, intl. memory_limit is unlimited.
    • System packages — git, unzip, patch, sqlite3. SQLite is what the baseline site installs run on.
    • Composer, pinned to a minor (composer:2.10) rather than to a floating 2. Composer is the largest single influence on what a run does, and its defaults change between minors — config.audit giving way to config.policy, say — so a minor bump is a deliberate commit that CI runs against rather than something that arrives in a published image unannounced. Patch releases, where fixes live, still flow in. Every report names the Composer version that produced it.
    • Plus a globally-required Composer plugin, mglaman/composer-drupal-lenient, pre-allow-listed.
    • The Drupdater app at /opt/drupdater/app/, which runs the addons' hooks and makes the run's commits — see below.
    • The Drupdater agent at /opt/drupdater/agent/, a second global plugin, which holds every addon and everything drupdater does to a site — see below. It ships drupdater's own Drush commands, the site facts query and the configuration resave, and brings ion-bazan/composer-diff with it as a library; that package's own plugin, and with it the composer diff command, is disabled.
    • Bundled tools at /opt/drupdater/tools/ — see below.

    Drupdater app¶

    drupdater/app, built from app/ in the Drupdater repository, is a PHP console application installed with its own dependencies at /opt/drupdater/app/. The binary runs it as /opt/drupdater/app/bin/drupdater in the working copy, through two hidden commands that read one JSON request on stdin and answer with one envelope on stdout, as the agent's do:

    Command Used by
    internal:fire Every event of a run that at least one addon hooks
    internal:commit The site update phase's commit of each site's exported configuration

    internal:fire carries the event, every addon the run runs with the stage it hooks each event at and what its hooks found so far, whether the run is a security run, and the author of the run's commits. The app orders the hooks by stage, calls composer drupdater:hook once per hook, makes the commits each asks for, and merges the pre-composer-update proposals. It answers with the findings it recorded, the merged plan, and the reason the run has nothing to do or the event failed — a failed event still answers with what its earlier hooks found, so the report keeps it.

    internal:commit commits exactly the paths each commit names, under the same rules as an addon's commits: no change, no commit, and nothing else may be staged.

    Drupdater agent¶

    drupdater/agent, built from agent/ in the Drupdater repository, is a Composer plugin installed globally. It holds every addon, and adds hidden composer drupdater:* commands through which Drupdater runs them and asks a project's own Composer — its repositories, its credentials, its configuration — without installing anything into it.

    Command Used by
    drupdater:addons The addons command, and the hooks of the addons a run builds: the addon catalogue
    drupdater:config Reading and checking .drupdater.yaml, for a run and the .drupdater.yaml valid check
    drupdater:hook Every addon hook of every run, one call per hook, from the app's internal:fire
    drupdater:report The run report's addon sections
    drupdater:merge-request The render merge request phase: the title and description, from the run report
    drupdater:handshake The drupdater agent installed in Composer preflight check, and the report's tool versions
    drupdater:platform-check The PHP platform requirements satisfied preflight check
    drupdater:project Staging the scaffold files an update rewrote, naming the update branch, and the site checks
    drupdater:install The composer install phase, and the update's install in update shared code
    drupdater:resolve The run's resolve update phase
    drupdater:site-install The baseline site install phase, and check --full
    drupdater:site-database, drupdater:site-restore Pointing each site at its throwaway database for the site update phase, and taking that off again
    drupdater:site-facts, drupdater:site-update, drupdater:config-export The site update phase: a site's facts, its update hooks, its configuration export

    drupdater:addons lists the catalogue: each addon, whether every run needs it, whether a normal run gets it when the project names none, and the stage it hooks each event at. It needs no project, so drupdater asks it from an empty directory.

    drupdater:config reads the .drupdater.yaml at the absolute path drupdater sends, layers it over the defaults, and checks it whole: its keys and their types, the timeout, the sites, and every addon name in both run types against the catalogue. It answers the sites, the timeout in nanoseconds, and for each run type the addons it runs — the mandatory ones first, then the configured ones or, for a normal run that names none, the defaults — and auto_merge. A file that fails a check is answered with a failed error whose reason says what to fix. It too needs no project.

    drupdater:hook runs one addon's hook for one workflow event. The request names the addon and carries the event — its name, plus what that event hands its hooks: the update plan on pre-composer-update, the committed composer.lock on post-composer-update, the site and its facts on the site events — with what the addon's own hooks found earlier in the run, and whether the run is a security run. The reply is what the hook returned: its finding, the commits it asks for, its proposal for the update, or the reason the run has nothing to do. The agent commits nothing itself; the app makes the commits before it calls the next hook.

    drupdater:report builds the addons' sections of the run report from what their hooks found. A section depends on its findings alone, so this too needs no project, and the final report can ask for it after the working copy is gone.

    drupdater:merge-request renders the merge request from the run report as it stands once every addon has finished: the title from its mode and started_at, the description from its addon sections. It too needs no project. A section it renders but cannot read fails the request rather than being left out; a section it has no renderer for is passed over. Over GitHub's 65,536-byte limit, it renders the description again without the dependency table's links.

    drupdater:resolve runs composer update --no-install --with-all-dependencies --ignore-platform-reqs --bump-after-update with the run's package restriction, pins and --minimal-changes, and reports each package that changed in the lock: upgraded, downgraded, removed or installed, with its versions as the lock prints them (1.x-dev 0424dff for a branch). A new commit of a branch counts as an upgrade, as in Composer's own output; a package that only moved between require and require-dev did not change. When the update cannot be resolved, Composer's own explanation is carried into the run's error. composer_patches runs the same update inside its own hook as a dry run, with --no-scripts, and puts composer.json and composer.lock back afterwards.

    drupdater:platform-check reports the platform requirements — of the locked packages and of the root package, require-dev included — that the running PHP does not meet, deciding each the way composer check-platform-reqs --lock does: a requirement is met when one candidate, the platform package itself or a package that provides or replaces it, satisfies every constraint on it. The project's config.platform is ignored, so the answer is about the real runtime.

    drupdater:project reports the web root — extra.drupal-scaffold.locations.web-root, without a trailing slash — and the lock's content-hash, which names the update branch. It is asked again whenever composer.json or the lock may have changed, so a reader never sees a stale answer.

    drupdater:install runs Composer's own install --optimize-autoloader --ignore-platform-reqs in its process, so the project's plugins and scripts run as in any composer install.

    The site commands each take the site they are about — its directory under sites/, and the SITE_NAME drush runs with — and run the project's own vendor/bin/drush, with drupdater's Drush commands loaded through --include:

    • drupdater:site-facts reads what drupdater and the addons read of a site in one bootstrap: its config sync and translation directories, its modules, its pending update hooks and, with update_status, the modules drupal.org no longer supports.
    • drupdater:site-update runs drush updatedb, saves every configuration object again so the export carries the update's new defaults, and reads the facts once more, without asking drupal.org.
    • drupdater:config-export runs drush config:export and names the directory it wrote, relative to the project, for drupdater to commit.
    • drupdater:site-database appends a block to the site's settings.php that points it at a SQLite database in a directory drupdater owns, and enables the sqlite module in core.extension.yml — excluded from the export — when the project does not use it itself. drupdater:site-restore cuts the block off again, leaving settings.php byte for byte as the project has it. drupdater:site-install does both around drush site:install --existing-config, without the standard profile.

    Each command reads one JSON request on stdin and prints one JSON reply on stdout, versioned by a protocol number the binary and the agent must agree on, with what the command logged. The agent ships in the same image as the binary, so they always do; the preflight check catches a binary run anywhere else.

    Bundled tools¶

    code_beautifier and deprecations_remover need PHPCS with drupal/coder and Drupal Rector. Rather than installing them into the project for each run, the image installs them once into /opt/drupdater/tools/, from the repository's tools/composer.lock, and runs them against the project from there. A project that already depends on drupal/coder or palantirnet/drupal-rector runs its own copy instead.

    rector/rector stays below 2.6.2, which removed rule sets Drupal Rector still relies on; Drupal Rector's own conflict holds it there.

    mglaman/phpstan-drupal is installed beside Drupal Rector so that Rector knows the type of a \Drupal::service() call; see deprecations_remover.

    The Composer environment is tuned for unattended runs; see environment variables for the values and why.

    The image build takes a VERSION build argument, which the release workflow sets to the tag being built, so the run report's drupdater_version field names the release the image came from.

    Volumes and the working directory¶

    Drupdater writes each site's SQLite database and private files to a directory of its own under the container's temp dir ($TMPDIR, else /tmp), removed when the run ends. Only the checkout itself needs to be mounted:

    docker run -v "$(pwd)":/workspace -w /workspace \
  ghcr.io/drupdater/drupdater-php8.3:latest \
  "$DRUPDATER_TOKEN" --working-dir /workspace

    Building locally¶

    make docker-build                                  # tags drupdater-local:latest
docker build --build-arg PHP_VERSION=8.4 -t drupdater-local:php8.4 .
make docker-run REPO=<git-url> TOKEN=<token>       # clone mode, for testing

    The Dockerfile is multi-stage: a Go build stage, then the PHP runtime image the binary is copied into.
